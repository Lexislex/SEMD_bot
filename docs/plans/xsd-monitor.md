# План: отслеживание XSD-схем в мониторе схематронов

Согласовано Claude и Codex (ревью в два круга). Ниже — итоговые решения.

## Проблема

`Schematron_Monitor` реагирует только на `schematron/**/*.sch`. Минздрав
выкладывает значимые для валидации изменения и в `xsd/` (например, СЭМД 289,
23.09.2026 и 12.10.2026: в `STRUCTURED_BODY.xsd` ослаблены `nullFlavor` и
`@unit`) — их бот пропустил. Цель: уведомлять об изменениях XSD для тех же
отслеживаемых СЭМД с теми же гарантиями (baseline, повтор до успешной доставки,
force-push, таймаут сравнения, обрезанные diff).

## Ключевое решение: независимый baseline на каждый вид артефакта

`schematron_watch.last_sha` — последний коммит, затронувший `schematron/`
(`get_last_commit(path="schematron")`). API коммитов GitLab фильтрует только по
одному `path`, поэтому один sha не покрывает обе папки. Отслеживать голову ветки
(baseline двигается на каждый коммит docx/xsl, меняется семантика сохранённых
baseline) или брать более свежий из двух коммитов (сравнение по датам хрупкое)
— отвергнуто.

Хранение — **отдельная таблица `xsd_watch`** той же структуры, а не составной
ключ в `schematron_watch`. Причина — безопасный откат: текущий
`SchematronStore.get_all()` строит словарь по `row[0]` (semd_oid), и после
отката кода XSD-строки в общей таблице затёрли бы схематроновые в меню, а
`get(oid)` без вида выбирал бы любую строку. С отдельной таблицей старый код её
просто не видит, обратная миграция не нужна; при откате XSD-состояния не
удаляем.

## Дизайн

### 1. Виды артефактов (`plugins/schematron_monitor/monitor.py`)

```python
@dataclass(frozen=True)
class ArtifactKind:
    key: str          # "schematron" | "xsd"
    directory: str    # "schematron" | "xsd"
    extensions: tuple # (".sch",) | (".xsd",)
    title: str        # заголовок сообщения
    hashtag: str      # "#схематрон" | "#XSD"

    def matches_path(self, path) -> bool: ...
    def matches_diff(self, diff) -> bool: ...

SCHEMATRON = ArtifactKind(...)
XSD = ArtifactKind(...)
ARTIFACT_KINDS = (SCHEMATRON, XSD)
```

- `is_schematron_path` / `is_schematron_diff` остаются тонкими обёртками над
  `SCHEMATRON.matches_*`.
- Отслеживается весь `xsd/`, включая `xsd/XSD CDA/coreschemas` — базовые схемы
  тоже влияют на валидацию.
- Имена классов не меняем: `SchematronMonitor`, `SchematronChange` (пакет,
  плагин, логгеры — всё `schematron_*`); докстринги обновляем на «schematron and
  XSD». В `SchematronChange` добавляется `kind: ArtifactKind = SCHEMATRON`.

### 2. Проверка и ошибки

- `check(semd_oid, kind=SCHEMATRON) -> Optional[SchematronChange]` — сигнатура
  и контракт сохраняются, `NotificationError` при прямом вызове пробрасывается
  как раньше.
- `check_all(semd_oids)`: на каждый OID один раз ищет СЭМД в 1520 и определяет
  репозиторий (638 / эвристика), затем перебирает `ARTIFACT_KINDS` через
  `_check_kind(semd_oid, kind, info, repo, prev)`.
  - Доставленное изменение добавляется в результат **сразу** после
    `_check_kind`.
  - `NotificationError` и прочие ошибки ловятся по виду: логируются, второй вид
    той же СЭМД всё равно проверяется.
  - `GitLabAuthError` прерывает весь цикл (токен общий); уже накопленные
    изменения возвращаются. Доставленный вид к этому моменту уже сдвинул свой
    baseline — потерь нет.
- Ошибки поиска/определения репозитория (`not_in_1520`, `no_git_link`,
  некорректный GIT_LINK) записываются в статус **обоих** видов, baseline каждого
  сохраняется.
- Смена репозитория/ветки тихо сбрасывает baseline обоих видов (как сейчас для
  схематрона).
- Нет коммитов в папке вида → статус `no_files` с подписью по виду
  («нет схематрона» / «нет XSD»); существующее значение `no_schematron` для
  схематрона сохраняется для совместимости с уже записанными строками.

### 3. Хранилище (`services/schematron_store.py`)

- `_ensure_table` создаёт `schematron_watch` (как есть) и `xsd_watch` с той же
  структурой (`CREATE TABLE IF NOT EXISTS`, без миграций).
- Внутри одного `SchematronStore` — фиксированный allowlist
  `{"schematron": "schematron_watch", "xsd": "xsd_watch"}`; SQL не дублируется,
  имя таблицы берётся только из allowlist.
- `get(semd_oid, kind="schematron")`, `get_all(kind="schematron")`,
  `save(state)` (таблица по `state.kind`). Старые вызовы без `kind` работают как
  раньше.
- `WatchState.kind: str = "schematron"` — новое поле в конце, с default; в БД
  не хранится (определяется таблицей).

### 4. Первый запуск для XSD

После деплоя `xsd_watch` пуста → в первом цикле каждая СЭМД получает тихий
XSD-baseline. Уже опубликованные изменения 289 автоматически **не**
объявляются.

Догон 289 — отдельное решение, не часть выкатки: ручной скрипт в `scripts/`,
который
- проверяет, что репозиторий/ветка совпадают с текущим разрешением, SHA полный и
  существует, и выбранный SHA предшествует обоим коммитам (23.09 и 12.10);
- не затирает существующий XSD-baseline без явного флага, показывает прежнее
  состояние.

Результат — **одно** уведомление по диапазону (оба коммита в списке), а не два
сообщения.

### 5. Вложения (общий путь скачивания полных файлов)

- Лимит числа полных файлов (например, 10) проверяется **до** скачивания и
  действует для всех путей: force-push, таймаут сравнения и обычный compare с
  множеством обрезанных diff. Превышен — не скачиваем ничего.
- Перед скачиванием файла из обрезанного diff проверяется
  `kind.matches_path(new_path)` (rename `xsd/foo.xsd` → вне `xsd/` не
  скачиваем).
- Фильтр по размеру переносится в монитор: после получения bytes файл больше
  `MAX_DOCUMENT_BYTES` в `attachments` не кладём. `MAX_DOCUMENT_BYTES` — одна
  константа в `monitor.py`, `handlers` импортирует её оттуда; защитная проверка
  в `_build_documents` остаётся. Это проверка после получения, а не лимит
  памяти при скачивании.
- В `SchematronChange` — список пропусков `skipped: List[Tuple[path, reason]]`,
  причины `limit_exceeded`, `download_failed`, `too_large` (могут сочетаться).
- Формулировки в сообщении по фактическому результату: «Приложены N файла(ов);
  часть файлов недоступна или превышает лимит — полный набор в GitLab», при
  `limit_exceeded` — «Файлов слишком много, не приложены — см. GitLab», а не
  безусловное «Текущая версия приложена».
- **Вне рамок:** сгенерированный `.diff` по-прежнему может отфильтроваться по
  размеру в `handlers`, при этом список файлов может ссылаться на «см. .diff».
  Старый крайний случай, исправляем только обещания для полных файлов.

### 6. Форматирование (`formatters.py`)

- Заголовок: `🧩 <b>Изменён схематрон СЭМД</b>` /
  `📐 <b>Изменена XSD-схема СЭМД</b>` — из `change.kind`.
- Ссылка «Папка {kind.directory}».
- Хэштеги `{kind.hashtag} #СЭМД_{oid}`.
- `diff_file_name`: `{kind.key}_{oid}_{from}_{to}.diff` (для схематрона имя не
  меняется).
- Отдельное сообщение на каждый вид, даже если в одном цикле изменились оба.

### 7. Меню (`handlers.py`)

- Строка по СЭМД: `• 289 Протокол… — SCH ✅ (изм. 26.05.2026) · XSD ✅`; дата
  показывается только при наличии `last_changed` (после тихого старта её нет —
  baseline не означает доставленное изменение).
- Меню запрашивает два набора: `get_all("schematron")` и `get_all("xsd")`.
- Тест на длину текста меню по реальному `WATCHED_SEMD` (лимит Telegram); если
  не влезает — сокращение названий/разбиение.
- Текст меню: «изменения схематронов и XSD-схем».

### 8. Метаданные плагина

`display_name` «🧩 Схематроны и XSD СЭМД», описание обновить. Имя плагина
`Schematron_Monitor`, callback data и конфиг не меняем. README плагина
обновить.

### 9. Тесты

`tests/test_schematron_monitor.py`, `tests/test_schematron_handlers.py`, новые
тесты хранилища:

- Основные сценарии монитора параметризованы по обоим видам.
- Коммит только с `.sch` не срабатывает для XSD, и наоборот; фильтрация
  расширений; rename/delete.
- Оба вида изменились → две доставки, оба в результате.
- Первая доставка успешна, у второго вида `NotificationError` / обычная ошибка /
  `GitLabAuthError` → первый результат сохранён, baseline второго не сдвинут;
  auth останавливает следующие OID. Обратный случай: первая неуспешна, вторая
  успешна.
- Лимит вложений N / N+1 → при превышении ноль `get_raw_file`, включая обычный
  compare с обрезанными diff; `too_large` и `download_failed` попадают в
  `skipped`, текст сообщения соответствует.
- Смена репозитория сбрасывает оба baseline тихо; ошибки lookup отражены в
  обоих видах.
- Хранилище: старые строки `schematron_watch` неизменны; XSD-состояние
  независимо; старые `get(oid)` / `get_all()` без `kind` возвращают только
  схематрон после появления XSD-строк.
- Меню: оба статуса, даты раздельно, длина в пределах лимита.

### 10. Выкатка и проверка

feature/xsd-monitor → PR в develop → релизный PR в master (автодеплой).

Проверка на проде после первого цикла:
- для каждой отслеживаемой СЭМД есть строка в `schematron_watch` и в
  `xsd_watch`, статусы объяснимы (`ok`, `no_files`, `repo_not_found` и т.п. —
  не обязательно все `ok`);
- создание `xsd_watch` не сбросило и не изменило существующие baseline
  схематронов; после цикла их продвижение объясняется обычными проверками и
  успешно доставленными изменениями;
- нет стартового шквала XSD-уведомлений (тихая инициализация); законные
  накопленные изменения схематронов допускаются.

Откат: откат кода без действий с БД; `xsd_watch` не удаляем.

## Решённые вопросы

1. Сообщения — отдельные на каждый вид.
2. XSD стартует тихо; догон 289 — отдельным ручным скриптом по решению
   пользователя.
3. Отслеживается весь `xsd/`, включая `coreschemas`.
